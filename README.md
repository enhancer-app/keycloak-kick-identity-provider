# Keycloak Kick Identity Provider

[![CI](https://github.com/enhancer-app/keycloak-kick-identity-provider/actions/workflows/ci.yml/badge.svg)](https://github.com/enhancer-app/keycloak-kick-identity-provider/actions/workflows/ci.yml)
[![License](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

A standalone, production-oriented [Keycloak](https://www.keycloak.org/) social identity provider
for [Kick](https://kick.com/) OAuth 2.1. It makes **Kick** available as a native provider in the
Keycloak Admin Console: administrators configure the normal identity-provider fields rather than
writing custom broker code.

This is a generic Keycloak extension. It has no application-specific realm, UI, database,
deployment topology, backend service, credential, or hosted-service assumption. It can be used by
any Keycloak deployment that runs a supported Keycloak version.

## Features

- OAuth 2.1 authorization-code flow with mandatory PKCE `S256`.
- Default Kick endpoints, configurable by realm administrators for controlled proxy/test deployments.
- Native Keycloak social-provider registration (`Kick` in Admin Console).
- Stable federated identity subject from only `data[0].user_id`.
- Optional e-mail import, avatar user attribute, declarative JSON attribute mapper, and two
  username strategies.
- Standard Keycloak first-login flow, sync modes (`IMPORT`, `FORCE`) and token-storage behavior.
- Strict profile/HTTP validation, bounded HTTP timeouts, and payload-safe errors/logging.
- Thin provider JAR: no bundled Keycloak, Jackson, HTTP client or logging libraries.
- Optional `kick` login theme with an accessible generic provider icon.

## Install

1. Download `keycloak-kick-identity-provider-<version>.jar` from the GitHub release.
2. Copy it into the Keycloak provider directory.
3. Run Keycloak’s build command.
4. Start Keycloak normally.

```bash
cp keycloak-kick-identity-provider-<version>.jar /opt/keycloak/providers/
/opt/keycloak/bin/kc.sh build
/opt/keycloak/bin/kc.sh start
```

For non-container distributions, use that distribution’s `providers/` directory and equivalent
`kc.sh build` command. Re-run `kc.sh build` after replacing or removing a provider JAR.

Open **Realm settings → Identity providers → Add provider**. `Kick` appears in the social
provider list. If it does not, see [Troubleshooting](#troubleshooting).

## Docker

The included Dockerfile uses the exact initial target image and performs Keycloak augmentation:

```bash
./gradlew clean jar
docker build -t keycloak-kick:local .
docker run --rm -p 8080:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin \
  -e KC_BOOTSTRAP_ADMIN_PASSWORD='<choose-a-local-password>' \
  keycloak-kick:local start-dev
```

`docker-compose.yml` provides the same local-only setup:

```bash
./gradlew jar
docker compose up --build
```

The compose admin password is deliberately a disposable local-development placeholder. Set a
strong deployment-specific administrator credential outside this repository for real use.

## Configure Kick

Create a Kick OAuth application and register the Keycloak broker callback URI exactly:

```text
https://<keycloak-host>/realms/<realm>/broker/<provider-alias>/endpoint
```

With default alias `kick`:

```text
https://<keycloak-host>/realms/<realm>/broker/kick/endpoint
```

This URI is generated by Keycloak and supplied as `redirect_uri` at both authorization and token
exchange. It must match the URI registered at Kick byte-for-byte. Use the publicly reachable
Keycloak origin and HTTPS outside local development.

In **Identity providers → Kick**, configure:

| Setting | Default | Notes |
| --- | --- | --- |
| Client ID | required | Issued by your Kick developer application. |
| Client Secret | required | Stored by Keycloak. Never commit it. Sent as `client_secret_post` only to Kick’s token endpoint. |
| Display name | `Kick` / Keycloak default | Login-button label. |
| Default scopes | `user:read` | Required profile scope. Extra scopes are a deliberate admin choice. |
| Sync mode | Keycloak default | Use `IMPORT` for one-time data import; `FORCE` refreshes brokered data on login. |
| Store tokens | off | Standard Keycloak storage control. Enable only when a downstream Keycloak feature requires upstream tokens. |
| Import e-mail | off | E-mail is optional profile data, never an identity key. |
| Store profile picture | on | Persists a validated absolute `http`/`https` URL as a user attribute. |
| Profile picture attribute | `kick_profile_picture` | Attribute name used when avatar storage is enabled. |
| Username strategy | `stable-id-prefix` | `kick-{user_id}` by default; safest across profile changes. |
| Username prefix | `kick-` | Used only by `stable-id-prefix`. |

The provider starts with these endpoint defaults; realm administrators may override them for
controlled proxy/test deployments:

```text
Authorization: https://id.kick.com/oauth/authorize
Token:         https://id.kick.com/oauth/token
Profile:       https://api.kick.com/public/v1/users
```

## OAuth behavior

Every login uses the authorization-code flow:

1. Keycloak sends the user to Kick with `response_type=code`, the configured scope, standard
   broker `state`, callback URI, and a newly generated PKCE `code_challenge`.
2. PKCE is always enabled with `code_challenge_method=S256`; it cannot be disabled or downgraded
   through realm import or the Admin REST API.
3. The broker callback exchanges the code using `grant_type=authorization_code`, `client_id`,
   `client_secret`, `redirect_uri`, and the original PKCE `code_verifier`.
4. The provider fetches the current user from Kick using `Authorization: Bearer <access token>`.

## Profile mapping and identity

Kick returns a payload shaped like:

```json
{
  "data": [
    {
      "user_id": 123,
      "name": "streamer",
      "email": "user@example.com",
      "profile_picture": "https://..."
    }
  ]
}
```

| Kick field | Keycloak use | Identity-critical? |
| --- | --- | --- |
| `data[0].user_id` | Federated identity subject; `kick.id` attribute | **Yes. The only identity key.** |
| `data[0].name` | `kick.login` and `kick.display_name`; source for optional `provider-username` | No; mutable. |
| `data[0].email` | Keycloak email and `kick.email` when supplied | No; optional. |
| `data[0].profile_picture` | `kick.profile_image_url` when supplied | No; optional and mutable. |

The provider never uses e-mail, name/login, channel name or avatar as a federated identity key.
It never guesses a first or last name because Kick does not provide reliable values for either.

The `Kick User Attribute Mapper` is available under the provider’s **Mappers** tab. It exposes the
raw validated profile document to Keycloak’s standard JSON attribute mapper, so administrators
can opt in to a mapping such as `data[0].name` without custom code.

## Username strategies

`stable-id-prefix` is the default and generates `kick-{user_id}`. It stays stable when the Kick
account changes its name and is the recommended option.

`provider-username` proposes Kick’s current `name`. It falls back to the stable-ID form when no
name is present. Since a name can change or collide with an existing Keycloak username, this can
trigger standard first-login review/account-link behavior. It never changes the federated identity
subject.

## Provider icon

The JAR includes an opt-in login theme named `kick`. Select it under **Realm settings → Themes →
Login theme** to add a generic Kick provider-button mark for the default `kick` alias. The bundled
mark is intentionally not an official Kick trademark asset.

For an existing custom login theme, do not switch themes. Add this to its `theme.properties`:

```properties
kcLogoIdP-kick=kc-social-kick
```

Then copy `theme/kick/login/resources/css/kick-idp.css` and
`theme/kick/login/resources/img/kick-idp-logo.svg` from this JAR/source into your theme. If your
provider alias differs, use `kcLogoIdP-<alias>` instead. Replace the generic SVG only after
reviewing the applicable Kick brand and trademark rules.

## Security model

- Only the three fixed HTTPS Kick endpoints are used; administrators cannot redirect requests to
  arbitrary hosts. This prevents endpoint misconfiguration and removes an SSRF/credential-leak
  configuration surface.
- The profile HTTP request has 5-second connection, socket and connection-pool timeouts and a
  256 KiB response limit.
- The provider rejects non-2xx profile responses, malformed JSON, absent/non-array/empty `data`,
  non-object `data[0]`, absent/invalid `user_id`, and absent access tokens.
- `user_id` must be a non-negative integral JSON value or numeric string. It is never coerced from
  a boolean, float, object, array, e-mail or display name.
- Profile pictures are stored only if they are absolute `http` or `https` URLs; `javascript:`,
  `data:`, relative and malformed values are dropped.
- Provider log messages and broker errors use fixed, actionable text plus safe status/reason
  metadata only. They never log authorization codes, access tokens, refresh tokens, client
  secrets, or full token/profile responses.
- Client secrets remain managed by Keycloak. Use Keycloak vault integration where appropriate for
  your deployment.

See [SECURITY.md](SECURITY.md) for private vulnerability reporting.

## Local development

Prerequisites: JDK 17. Docker is needed only for the container smoke test and Docker image build.
The repository includes the Gradle Wrapper, so a global Gradle installation is not needed.

```bash
./gradlew clean build
./gradlew test -PwithSmoke
docker build -t keycloak-kick:local .
```

`-PwithSmoke` pulls and starts `quay.io/keycloak/keycloak:26.5.2`, mounts the just-built provider
JAR, and verifies via the Admin REST API that Keycloak discovers provider id `kick`.

For a real Kick test application, follow [docs/MANUAL_E2E.md](docs/MANUAL_E2E.md).

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Kick is absent from **Add provider** | Confirm the JAR is under `/opt/keycloak/providers/`, run `kc.sh build`, restart, and inspect server startup logs for provider-loading errors. |
| `Invalid redirect_uri` at Kick | Compare the registered URI with Keycloak’s broker callback exactly: scheme, host, port, realm, alias, path and trailing slash. |
| Login fails after returning from Kick | Verify the Keycloak instance can reach `https://id.kick.com` and `https://api.kick.com`; check client ID/secret and scope; do not paste token responses into logs/issues. |
| User not linked as expected | Inspect the federated identity link. Its subject must be Kick `data[0].user_id`; name/e-mail/channel/avatar do not select a Keycloak account. |
| E-mail is blank | Expected unless **Import e-mail** is enabled and Kick supplied an e-mail. Treat it as optional. |
| Avatar attribute is blank | Confirm avatar storage is enabled and Kick returned an absolute `http`/`https` `profile_picture`. |
| Icon is missing | Select the bundled `kick` theme or add `kcLogoIdP-<alias>=kc-social-kick` and the provided resources to an existing login theme. |
| Upgrade breaks provider loading | Stop the rollout, return to the prior compatible Keycloak/plugin pair, then follow [Compatibility](docs/COMPATIBILITY.md). |

## Upgrade guidance

1. Read [docs/COMPATIBILITY.md](docs/COMPATIBILITY.md) before changing Keycloak versions.
2. Back up your realm configuration and existing federated identity links.
3. Test the target Keycloak image plus new provider JAR in staging.
4. Run `./gradlew test -PwithSmoke` for the source release and execute the manual E2E login.
5. Replace the JAR, run `kc.sh build`, restart Keycloak, and verify `Kick` in the Admin Console.
6. Keep the provider alias stable. Changing an alias changes the callback URI and may require
   reconfiguring Kick and reviewing identity-provider links.
